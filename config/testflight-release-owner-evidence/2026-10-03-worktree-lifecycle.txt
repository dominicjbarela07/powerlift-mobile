### Working Directory / Scope
/Users/dominic/powerlifting_app_dev

This supplements the permanent DEV/TestFlight release invariants.

Codify this rule in the same authoritative repository governance used by `docs/RELEASE_INVARIANTS.md` and enforce it in Codex/release workflows.

The problem is NOT that worktrees may never be used.

The problem is that temporary worktrees are being created, work is being shipped, and those worktrees are then left around indefinitely. We accumulate old branches/worktrees containing different pieces of product state, lose track of which one owns what, and eventually established work gets omitted or overwritten.

THAT STOPS NOW.

## Fundamental Law

A temporary worktree has a lifecycle:

CREATE IF ACTUALLY NEEDED
→ DO THE WORK
→ VALIDATE
→ RECONCILE WITH CANONICAL DEV
→ if authorized, SHIP
→ RECONCILE FINAL SHIPPED STATE BACK INTO CANONICAL DEV
→ VERIFY NOTHING UNIQUE REMAINS STRANDED
→ CLOSE/REMOVE THE TEMPORARY WORKTREE

A worktree is NOT a permanent storage location for shipped product work.

### 1. CANONICAL DEV REMAINS THE DURABLE DEVELOPMENT STATE

The normal DEV workspace is intentionally allowed to be dirty.

Do NOT create a new worktree merely because:

- DEV has uncommitted changes
- DEV is messy
- isolation feels cleaner
- Codex prefers a pristine checkout
- release tooling would be easier from another directory

Dirty DEV is expected.

A temporary worktree may be created when there is a concrete technical reason for isolation, but Codex must state that reason.

### 2. WORKTREES ARE TEMPORARY

When Codex creates a worktree, record:

- worktree path
- branch
- starting SHA
- purpose
- source DEV state
- what changes are being made there

That worktree now has an explicit obligation to be reconciled and closed.

Do not leave it indefinitely because the immediate task finished.

### 3. SHIPPING ENDS THE WORKTREE'S OWNERSHIP

If I authorize:

`send it to TestFlight`
`push it`
`deploy it`
`release it`

and work from a temporary worktree is included in that release, then after successful publication:

THE TEMPORARY WORKTREE MAY NOT REMAIN THE ONLY PLACE THAT WORK EXISTS.

Required sequence:

temporary worktree changes
→ TestFlight candidate
→ validation
→ publication
→ exact published state identified
→ reconcile/back-propagate into canonical DEV
→ synchronize any other still-legitimate active development worktrees as necessary
→ prove no unique shipped state remains stranded
→ remove/close the completed temporary worktree

Do this IN THE SAME RUN.

### 4. TESTFLIGHT → DEV RECONCILIATION HAPPENS BEFORE CLEANUP

Never remove a worktree until its valid state has been accounted for.

Before cleanup, compute:

TEMPORARY WORKTREE
vs
CANONICAL DEV
vs
PUBLISHED TESTFLIGHT

Determine whether the temporary worktree contains anything unique.

If unique VALID product work exists:

→ integrate it into canonical DEV first.

If something is ambiguous:

→ DO NOT delete it.
→ report it to me.

If it is clearly obsolete temporary/release scaffolding:

→ it may be removed with the worktree.

The goal is not blindly deleting worktrees.

The goal is ensuring they stop becoming hidden competing sources of truth.

### 5. DEV SUPERSET LAW STILL CONTROLS EVERYTHING

Permanent invariant:

DEV ⊇ TESTFLIGHT

Therefore after shipping from any worktree:

PUBLISHED TESTFLIGHT - CANONICAL DEV = ∅

If that is not true:

THE RELEASE WORKFLOW IS NOT FINISHED.

Back-propagate the valid published state into DEV before declaring completion.

Never nerf TestFlight to make this equation true.

Bring DEV forward.

### 6. SYNC OTHER ACTIVE WORKTREES WHEN NECESSARY

If there are other ACTIVE worktrees containing legitimate ongoing work, do not leave them based on stale product foundations after a release.

Determine whether the shipped/reconciled state needs to be incorporated into them.

If yes:

canonical DEV / published cumulative state
→ sync into active worktree
→ preserve that worktree's legitimate unshipped changes

Do not overwrite its ongoing work.

Do not blindly merge everything everywhere.

The purpose is to prevent active worktrees from later reintroducing stale product state.

### 7. CLOSE COMPLETED WORKTREES

After a worktree's task has:

- been completed,
- reconciled,
- shipped if authorized,
- back-propagated to DEV,
- and had all unique valid work accounted for,

REMOVE THE WORKTREE.

Also clean up its temporary branch/ref when safe and when it has no remaining purpose.

Do not leave:

`full-sync-20260929`
`rest-timer-fix`
`education-review-old`
`release-whatever`
`hotfix-whatever`

sitting around months after their work was integrated.

Completed worktrees are not archives.

Git history/release records are the archive.
